# Preview Connection Errors

<Frame>
  <img src="https://cdn.shopify.com/s/files/1/0838/0052/3057/files/studio-load-failed.png?v=1773627934" alt="Weaverse Studio preview loading failed error state" />
</Frame>

When working with Weaverse Studio, you may encounter preview connection errors that prevent the live preview from loading. This guide helps you quickly diagnose and resolve these issues.

## Common Error Types

### CONNECTION_TIMEOUT

**Symptom**: Studio shows **"Your preview isn’t ready yet"** or **"Studio can't open this Oxygen preview"**. The side panels show **Preview not connected**. The preview did not answer Studio in time. Studio cannot tell why: a timeout does not prove the site is offline, requires sign-in, or is private.

**For a hosted preview**:

1. Check the selected URL in **Manage previews**. Open that exact URL in a separate, regular tab in the same browser profile.
2. If the storefront asks for a customer or B2B account, follow [Sign-In and Cookies](#sign-in-and-cookies). If Oxygen asks you to sign in as a **staff member of the Shopify store**, see [Private Oxygen Environment](#private-oxygen-environment).
3. If the site doesn't load in the tab, check the URL, deployment status and any VPN or firewall requirements with your developer. When the URL is ready, return to Studio and choose **Check again**.

**For a local preview**:

1. Run `npm run dev` in your theme project and keep it running.
2. Check the URL and port in the terminal. Pilot uses `http://localhost:3456` by default. Select that URL in **Manage previews**.
3. If Chrome asks to let Studio access other apps and services on this device, choose **Allow**, then click **Check again**.
4. Safari blocks HTTP previews inside Studio. Use Chrome or Firefox, or an HTTPS preview URL. For an HTTP preview on a local network address, try `localhost` if the server runs on this computer, or use an HTTPS URL.

If a developer is setting up your storefront, ask them to finish the preview setup.

### Sign-In and Cookies

1. Open the **exact preview URL selected in Studio** in a separate, regular tab in the **same browser profile**. Sign in to the storefront as you normally would. Signing in to a different domain, even for the same store, may not sign you in to the preview.
2. Return to Studio. A storefront that recognizes you in its own tab might not recognize you inside Studio. If needed, use only the site-specific cookie or storage permission described below for your browser.
3. Choose **Check again** (or **Retry**) in Studio. Remove any exception if it doesn't help or you no longer need it.

These options are for desktop browsers in normal browsing mode. Private windows and managed profiles can have different rules.

- **Chrome:** Open **Settings → Privacy and security → Third-party cookies**. Under **Sites allowed to use third-party cookies**, choose **Add** and enter `https://studio.weaverse.io`, the top-level site where the preview runs. This exception applies to embeds on Studio, not just this preview. Don't use a wildcard or change the default for all sites. [Chrome cookie settings](https://support.google.com/chrome/answer/95647?co=GENIE.Platform%3DDesktop&hl=en)
- **Edge:** While you're on Studio, Edge may ask whether another site can use its cookies and site data. Allow it only if the requesting site is your trusted preview. The permission is temporary and applies while you're on the site where the prompt appeared. [Microsoft's guide to temporary permissions](https://support.microsoft.com/en-us/edge/temporarily-allow-cookies-and-site-data-in-microsoft-edge)
- **Firefox:** Total Cookie Protection gives an embedded site separate storage for each top-level site. If the trusted preview requests access to its cookies inside Studio, you can grant that site-specific request. Leave Enhanced Tracking Protection on. [Mozilla on partitioned cookies and storage access](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Third-party_cookies)
- **Safari on Mac:** Safari's Privacy settings don't have a general per-site exception for cross-site cookies. Leave **Prevent cross-site tracking** on. If the trusted preview supports storage access and asks for it inside Studio, you can allow that request. If no prompt appears, try another approved browser or ask your storefront developer for help. [Safari Privacy settings](https://support.apple.com/guide/safari/privacy-sfri35610/mac) · [WebKit on storage access](https://webkit.org/blog/11545/updates-to-the-storage-access-api/)
- **Brave:** With **Studio** open, select the **Shields** lion in the address bar and expand **Advanced controls** (or **Advanced options**). Change only the cookie setting to allow cookies for **this site**. Keep Shields on and leave the trackers and ads setting unchanged. [Brave's cookie control](https://support.brave.app/hc/en-us/articles/360022806212-How-do-I-use-Shields-while-browsing) · [Site-specific Shields settings](https://support.brave.app/hc/en-us/articles/360023646212-How-do-I-configure-global-and-site-specific-Shields-settings)
- **Other or managed browsers:** Use a documented site-specific permission if one is available. Otherwise, try a supported browser approved by your organization or ask your administrator.

Signing in or granting a permission is not a guarantee. The browser may keep the two sessions separate, a cookie's `SameSite` setting may keep it from being sent inside Studio, or the preview may never request storage access. Studio cannot inspect a sign-in redirect inside a cross-origin preview. If it still doesn't connect, ask the storefront developer or support to check whether this preview supports embedded sign-in. Keep storefront authentication and global privacy protections in place.

### Private Oxygen Environment

Use this section only if the preview shows Oxygen's **Shopify staff sign-in** or the environment owner has confirmed that its **URL privacy** is **Private**. A `.myshopify.dev` hostname identifies an Oxygen URL, not the cause of a timeout. A customer or B2B login page is not the staff gate; use [Sign-In and Cookies](#sign-in-and-cookies) for that case.

Oxygen's staff sign-in page cannot open in Studio's preview frame. A browser cookie exception doesn't change the environment's URL privacy.

**Option A: Use a public Oxygen URL**

Only an authorized store operator should make the environment public. This removes the staff gate for anyone with the URL. Keep the storefront's own customer authentication in place. If removing the staff gate isn't acceptable, keep the environment private.

1. In Shopify admin, open your **Hydrogen storefront**.
2. Open **Storefront settings** → **Environments and variables**.
3. Click the environment used by your preview URL.
4. Under **URL privacy**, select **Public**, then click **Save**.
5. Select the approved URL in **Manage previews** and choose **Check again**.

[Shopify's public environment limits](https://shopify.dev/docs/storefronts/hydrogen/deploy/oxygen/environments#public-environment-limits) apply per store:

| Store plan | Public environments |
| --- | --- |
| Shopify Plus | 25 |
| Most other plans | 1, usually already used by production |
| Development stores and trial plans | 0 |

For the full deployment steps, see [Publish Your Storefront & Update Weaverse Preview URL](/guides/deployment/oxygen).

**Option B: Use an approved public URL on another host**

If a public preview is appropriate but the store has no public Oxygen environment available, the developer can evaluate another host, such as [Cloudflare Workers](/guides/deployment/workers). This requires a migration and validation. It is not a fix for a customer sign-in cookie.

Open **Manage previews** in Studio, add and select the new public URL, then click **Check again**.

### NO_WEAVERSE_CONTENT

**Symptom**: The preview loads, but Studio shows **"No Weaverse content on this page yet"** with setup guidance — *not* a connection error. The URL responded; it just has no Weaverse sections for Studio to edit.

<Note>
This is a normal, recoverable state — not a broken preview. Studio stays connected on any page it can reach (including 404s and routes without Weaverse content) so it can tell you *why* there's nothing to edit, instead of falsely reporting "Connection lost". Requires `@weaverse/hydrogen` **5.16.3+** in your theme.
</Note>

**Common Causes**:
- No page or template has been created/assigned for this route yet
- The underlying Shopify resource (collection, product, article) doesn't exist, or isn't published to your **Headless / Hydrogen sales channel** — the storefront route then returns a 404 with no content to edit
- The route doesn't render `<WeaverseHydrogenRoot />`
- Missing or outdated `@weaverse/hydrogen` package

**How to set it up**:

1. **Create or assign a page for this route**
   - Open the page selector in the Studio top bar and create/assign a page for the current URL
   - Add at least one section, then **Save**

2. **For a Shopify resource page, confirm the resource exists and is published**
   - In Shopify admin, verify the collection/product/article in the URL exists
   - Publish it to your **Headless** (Hydrogen) sales channel — an unpublished resource returns a 404, so the storefront renders its not-found page with no Weaverse content
   - Open the URL directly in your browser: a 404 there confirms the Shopify resource, not Weaverse, is missing

3. **Verify the route renders Weaverse content**
   - The route loader should call `weaverse.loadPage()` and the route should render `<WeaverseHydrogenRoot />`
   - Ensure components are registered in `app/weaverse/components.ts` (imported as `~/weaverse/components` in Pilot)
   - Restart the dev server after adding new components

4. **Confirm the page type is supported**
   - Supported types: `PRODUCT`, `COLLECTION`, `PAGE`, `BLOG`, `ARTICLE`, `INDEX`, `CUSTOM`
   - Some routes (search, cart, account) use native Shopify components and aren't Weaverse pages

5. **Update Weaverse if needed**
   ```bash
   # Hydrogen 2026.10.3 and later (latest: @weaverse/hydrogen 6.5.1)
   npm install @weaverse/hydrogen@^6.5.0 @shopify/hydrogen@^2026.10.3
   # Classic Hydrogen (2026.4 and earlier)
   npm install @weaverse/hydrogen@^5
   ```

   `@weaverse/hydrogen@latest` installs v6, which requires Hydrogen 2026.10. To move a classic theme to v6, follow the [v6 migration guide](/migration-advanced/v6-migration).

<Note>If you just created a page, make sure it uses the Weaverse page template and has sections configured. See the [Rendering Weaverse Pages guide](/guides/rendering-page) for complete implementation details.</Note>

### INVALID_URL

**Symptom**: Preview shows "Invalid preview URL" immediately.

**Common Causes**:
- Malformed URL in project settings
- Missing protocol (http/https)
- Invalid characters in URL
- Localhost URL when expecting production

**Quick Fixes**:

1. **Check project preview URL settings**
   - Go to Project Settings in Weaverse Studio
   - Verify preview URL format: `http://localhost:3456` (development)
   - Ensure no trailing slash or extra characters

2. **Validate URL format**
   - Must include protocol: `http://` or `https://`
   - Use `localhost` not `127.0.0.1` for local development
   - Check for typos in domain name

3. **Reset preview URL**
   - Delete current preview URL
   - Enter fresh URL: `http://localhost:3456`
   - Save and refresh Studio

### AUTH_REQUIRED

If opening the exact preview URL prompts for access, check who is asking:

- **Storefront customer or B2B account:** Follow [Sign-In and Cookies](#sign-in-and-cookies). Keep the store's sign-in requirement.
- **Shopify staff access to an Oxygen environment:** See [Private Oxygen Environment](#private-oxygen-environment).
- **Development server, proxy or corporate network:** Ask the preview owner or network administrator to confirm your access. Use the normal sign-in method for that service.

### CORS_ERROR

**Symptom**: Browser console shows CORS policy errors.

**Common Causes**:
- Missing CORS headers in development server
- Incorrect origin configuration
- Browser security restrictions
- Proxy/middleware blocking requests

**Quick Fixes**:

1. **Check the CSP for Studio's sources**

   Studio embeds your storefront in an iframe and loads its bridge script from the Studio origin. Merge `getWeaverseStudioCspDirectives(request)` (`@weaverse/hydrogen` 6.3.0+) into the directives you pass to Hydrogen's `createContentSecurityPolicy`. On Studio requests it adds the Studio origin to `frame-ancestors`, `script-src`, `connect-src`, `style-src`, `font-src` and `img-src`, plus `'unsafe-eval'` in design mode; for normal visitors it returns `{}`:

   ```typescript
   // app/weaverse/csp.ts (excerpt)
   const studio = getWeaverseStudioCspDirectives(request);
   for (const key of Object.keys(studio) as (keyof typeof studio)[]) {
     directives[key] = [...(directives[key] ?? []), ...(studio[key] ?? [])];
   }
   ```

   The helper trusts only `https://` hosts on `weaverse.io` or `weaverse.dev`. A self-hosted Studio on another domain gets `{}`, so add its origin to your own directives.

2. **Append Studio's sources, don't replace yours**

   Overwriting a directive with Studio's array drops your own sources, such as `'unsafe-inline'` in `script-src`, which React Router's hydration scripts need when the policy has no nonce. Look for `violates the following Content Security Policy directive` in the console and add the blocked origin to the directive it names. See the [Content Security Policy guide](/features/content-security) for the setup and a rollout checklist.

3. **Enable CORS for local development**
   ```typescript
   // vite.config.ts
   server: {
     cors: true,
     // or more specific:
     cors: {
       origin: ['https://studio.weaverse.io', 'https://*.weaverse.io'],
       credentials: true
     }
   }
   ```

4. **Restart development server**
   - Stop server (Ctrl+C)
   - Clear cache: `rm -rf .cache`
   - Restart: `npm run dev`

<Warning>**Production Note**: Never use `cors: true` in production. Configure specific origins for your Weaverse Studio domain. Use `Content-Security-Policy-Report-Only` during development to monitor violations before enforcing.</Warning>

## Advanced Troubleshooting

### Check Browser Console

1. Open browser DevTools (F12 or Cmd+Option+I)
2. Go to **Console** tab
3. Look for red error messages
4. Copy error messages for support

### Network Inspector

1. Open DevTools → **Network** tab
2. Refresh preview
3. Look for failed requests (red status)
4. Check request/response headers
5. Note status codes (404, 500, etc.)

### Verify RPC Communication

The preview uses PostMessage/RPC for Studio communication:

```javascript
// Check whether the Weaverse storefront runtime booted in the preview.
// @weaverse/hydrogen stores runtimes by Weaverse page ID.
const runtime = Object.values(window.__weaverses ?? {})[0]
runtime?.sdkVersion // e.g. "6.1.0" when a runtime is mounted
runtime?.isDesignMode // true when the page is rendered inside Studio

window.__weaverses // Record<pageId, Weaverse runtime>
```

<Note>
Check the storefront runtimes in `window.__weaverses`, not the Studio bridge. The bridge object is an internal implementation detail and does not expose a stable `version` field.
</Note>

### Clear Studio Cache

1. In Weaverse Studio, press **Cmd+Shift+R** (Mac) or **Ctrl+Shift+R** (Windows)
2. This forces a hard refresh and clears cached preview state

### Test with Different Browser

For a signed-in preview, start with [Sign-In and Cookies](#sign-in-and-cookies). If you try another approved browser, sign in on the exact preview URL in that browser's normal profile before checking Studio again.

## Getting Help

If you've tried all troubleshooting steps and still experiencing issues:

1. **Check System Status**
   - Visit [status.weaverse.io](https://status.weaverse.io) for known issues

2. **Community Support**
   - Join [Weaverse Discord](https://discord.gg/weaverse)
   - Search [GitHub Discussions](https://github.com/orgs/Weaverse/discussions)

3. **Contact Support**
   - Email: support@weaverse.io
   - Include:
     - Error type from preview overlay
     - Browser and OS version
     - Node.js version (`node --version`)
     - Package versions from `package.json`
     - Relevant error messages, without cookies, authentication headers or sign-in URLs

## Prevention Tips

### Development Best Practices

1. **Always run dev server before opening Studio**
   ```bash
   npm run dev
   ```

2. **Keep packages updated**
   ```bash
   npm update @weaverse/hydrogen
   ```

3. **Use recommended Node.js version**
   - Node.js 22.18+ or 24.11+ for the current Pilot template
   - Check with `node --version`

4. **Monitor terminal output**
   - Watch for server errors
   - Note the actual port being used
   - Check for build warnings

### Common Configuration

**Recommended `vite.config.ts` for preview:**

```typescript
import { defineConfig } from 'vite'

export default defineConfig({
  server: {
    port: 3456,
    cors: true,
    host: 'localhost',
    strictPort: false, // Try next port if 3456 is busy
  },
})
```

**Recommended project settings:**

- **Preview URL**: `http://localhost:3456`
- **Auto-reload**: Enabled
- **HTTPS**: Disabled for local development
