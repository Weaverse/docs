# Weaverse v6 & Hydrogen 2026.10

<Visibility for="agents">
> **Agent note:** This page migrates a storefront from classic Hydrogen (2026.4 and earlier) with `@weaverse/hydrogen` 5.x to Hydrogen 2026.10 with `@weaverse/hydrogen` 6. The "Before" samples show the old code being removed. For v6 projects, import Weaverse from `@weaverse/hydrogen/react-router`, query Shopify with `storefront.graphql(gql(...), { variables, cache })`, and never use `CartForm`, `Analytics.Provider`, `createHydrogenContext`, `storefront.query()`, the `hydrogen()` Vite plugin, `weaverse.withCache` or the `WeaverseHydrogen` class. Create `WeaverseClient` from the request's Storefront client, and pass the market as its `locale` option (`@weaverse/hydrogen` 6.1.0+) when the Storefront client's `i18n.language` is a Shopify `LanguageCode` such as `ZH_TW`. Deploy with `shopify hydrogen deploy --assets-dir dist/client --worker-dir dist/server`. Pilot `main` (Weaverse/pilot#209) is the reference implementation.
</Visibility>

`@weaverse/hydrogen` 6 runs on **Hydrogen 2026.10**, the release where Shopify turns Hydrogen from a framework into a library of server handlers and client stores. This guide moves a Weaverse Hydrogen storefront from classic Hydrogen (2026.4 and earlier, `@weaverse/hydrogen` 5.x) to Hydrogen 2026.10 and `@weaverse/hydrogen` 6, the same way the [v5 guide](/migration-advanced/v5-migration) covered the move to React Router v7.

Every sample on this page comes from [Pilot](https://github.com/Weaverse/pilot), which made this move in [Weaverse/pilot#209](https://github.com/Weaverse/pilot/pull/209) and shipped it as [v2026.11.7](https://github.com/Weaverse/pilot/releases/tag/v2026.11.7). Samples are trimmed; `// ...` marks omitted code.

## What Changed and Why

Classic Hydrogen owned the request: `createHydrogenContext()` built the storefront client, cart, session and customer account, `createRequestHandler` from `@shopify/hydrogen/oxygen` ran React Router, the `hydrogen()` Vite plugin and `shopify hydrogen dev` drove development, and components such as `CartForm`, `Analytics.Provider`, `Image` and `Money` came from the package.

Hydrogen 2026.10 is a **server-handler library**. Your app composes the request lifecycle itself and calls into Hydrogen where it needs Shopify:

| Concern | Classic Hydrogen (2026.4) | Hydrogen 2026.10 |
| --- | --- | --- |
| Request lifecycle | `createHydrogenContext()` + `createRequestHandler` from `@shopify/hydrogen/oxygen` | Your `server.ts`: `createShopifyRequestContext`, `createStorefrontClient`, `handleShopifyRoutes`, `handleShopifyRedirects`, React Router's `createRequestHandler` |
| Tooling | `shopify hydrogen dev/build`, `hydrogen()` Vite plugin, GraphQL codegen | `vite dev`, `react-router build`, `gql()` with `@shopify/hydrogen/ts-plugin` |
| Storefront API | `storefront.query()`, throws on errors, default cache | `storefront.graphql()`, returns `{ data, errors }`, no default cache |
| Cart | `context.cart`, `CartForm`, a `/cart` action | `createCartServerHandlers()` at `/api/cart`, `createCartComponents()` store |
| Product form | `useOptimisticVariant`, `getAdjacentAndFirstAvailableVariants` | `createProductComponents()`: `ProductProvider`, `useProductForm` |
| Analytics | `Analytics.Provider`, `Analytics.ProductView`, ... | `ShopifyScripts` and the `window.Shopify.analytics` bus |
| Customer Account | `context.customerAccount.login()` in your routes | `createCustomerAccountServerHandlers()` at fixed `/account/*` paths |
| UI helpers | `Image`, `Money`, `Pagination`, `getSeoMeta`, sitemaps, CSP | Removed: port them into your theme |

`@weaverse/hydrogen` 6 follows: `WeaverseClient` takes the 2026.10 Storefront client instead of a classic Hydrogen context, and the SDK ships one entry point per framework.

## Supported Versions

| Package | Version |
| --- | --- |
| `@shopify/hydrogen` | `2026.10.x` (Pilot uses `^2026.10.2`) |
| `@weaverse/hydrogen` | `6.x` (Pilot uses `^6.1.0`; the `locale` option needs 6.1.0) |
| `@weaverse/react` / `@weaverse/next` | Pinned by `@weaverse/hydrogen`: `6.1.0` / `1.1.1` for 6.1.0, `6.0.0` / `1.1.0` for 6.0.0 |
| `@shopify/cli` (dev) | `4.4.0` or later, for `shopify hydrogen deploy` (Pilot uses `^4.9.4`) |
| `react-router`, `@react-router/dev` | `7.18` or later 7.x, both on the same version (Pilot uses `7.18.5`) |
| `vite` | `8` |
| `@shopify/mini-oxygen` | `^4.2.3` |
| Node.js | `^22.18 \|\| ^24.11` (Pilot's `engines`) |

Themes on Hydrogen 2026.4 or earlier stay on `@weaverse/hydrogen` 5.x. React Router 8 is not supported yet.

<Warning>
  `@weaverse/hydrogen`, `@weaverse/react` and `@weaverse/next` are released together as one version group: `@weaverse/hydrogen` 6.1.0 depends on exactly `@weaverse/react` 6.1.0 and `@weaverse/next` 1.1.1 (6.0.0 on `@weaverse/react` 6.0.0 and `@weaverse/next` 1.1.0). If your `package.json` also lists `@weaverse/react` or `@weaverse/next`, align them to the versions your `@weaverse/hydrogen` pins. Mismatched versions install two copies of `@weaverse/react` with separate React contexts, and Weaverse components stop finding their data.
</Warning>

## Before You Begin

This is a major upgrade with breaking changes across the whole theme. Before you start:

1. **Commit everything** and work on a branch.
2. **Read Shopify's migration skill.** `@shopify/hydrogen` 2026.10 ships one at `node_modules/@shopify/hydrogen/skills/migrate-to-hydrogen-2026-10/`, with one reference file per area (cart, analytics, customer account, ...). Install `@shopify/hydrogen@2026.10` first, or read it in a fresh Pilot checkout.
3. **Keep Pilot's cut-over open** as a reference: the [PR diff](https://github.com/Weaverse/pilot/pull/209/files) and the spec at `.weaverse/specs/2026-10-29-hydrogen-2026-10-cut-over.md` in the Pilot repo, which lists every decision and its reason.
4. **Plan for a full regression pass.** Cart, product forms, analytics and customer accounts are rewritten, not renamed.

<Warning>
  Classic projects should pin `@shopify/hydrogen` to `~2026.4.x` until they migrate. A `^2026.4.0` range resolves to 2026.10, whose `hydrogen()` Vite plugin only throws an error telling you to pin.
</Warning>

## Migration Options

### Option 1: Start From the Latest Pilot (Recommended)

If your theme is close to Pilot, create a new project from the current Pilot and move your customizations over:

```bash
npx @weaverse/cli@latest create \
  --template=pilot \
  --project-id="your-project-id" \
  --project-name=my-storefront
```

Then copy your sections and components into `app/sections/` and `app/components/`, run the codemod from [Step 2](#step-2-run-the-weaverse-codemod) on them, and port each Storefront API query to `gql()` ([Step 6](#step-6-move-queries-to-the-new-graphql-client)). Your Weaverse project, pages and theme settings are not affected: point the project's preview URL at the new storefront.

### Option 2: Upgrade in Place

Follow the steps below. They follow the order Pilot used, so the project builds again as early as possible.

## Step 1: Update Dependencies, Scripts and Config

### Dependencies

```bash
npm install @shopify/hydrogen@^2026.10.2 @weaverse/hydrogen@^6.1.0 \
  react-router@7.18.5 @react-router/dev@7.18.5
npm install -D gql.tada @types/node @shopify/mini-oxygen@^4.2.3 @shopify/cli@^4.9.4
npm uninstall @shopify/hydrogen-codegen @graphql-codegen/cli
rm codegen.ts storefront-api.generated.d.ts customer-account-api.generated.d.ts
```

`@shopify/cli` stays a dev dependency for `shopify hydrogen deploy`, `link` and `env pull`. It must be 4.4.0 or later: older versions, including every 3.x release, don't support the `--assets-dir` and `--worker-dir` flags the new `deploy` script uses. Pilot uses `^4.9.4`.

### Scripts

**Before (classic):**

```json
{
  "scripts": {
    "build": "shopify hydrogen build --codegen",
    "dev": "react-router typegen && shopify hydrogen dev --codegen --port 3456",
    "preview": "shopify hydrogen preview --build",
    "typecheck": "tsc --noEmit",
    "codegen": "shopify hydrogen codegen"
  }
}
```

**After (Hydrogen 2026.10):**

```json
{
  "scripts": {
    "build": "react-router build",
    "dev": "hydrogen skills check --mode=warn && vite dev --port 3456",
    "dev:https": "hydrogen skills check --mode=warn && vite dev --port 3456",
    "preview": "react-router build && vite preview --port 3456",
    "start": "vite preview --port 3456",
    "typecheck": "react-router typegen && tsc --noEmit && hydrogen gql check --fail-on-warn",
    "deploy": "shopify hydrogen deploy --assets-dir dist/client --worker-dir dist/server"
  }
}
```

The `hydrogen` binary ships with `@shopify/hydrogen`. `dev:https` runs the same command; `vite.config.ts` reads `npm_lifecycle_event` to turn on local HTTPS, which Customer Account login needs.

### Deploy

Classic projects built with `shopify hydrogen build` and deployed with a bare `shopify hydrogen deploy`, which knew where Hydrogen's build put its output. On 2026.10 the app builds with `react-router build`, which writes the browser assets to `dist/client` and the Oxygen worker to `dist/server`, so Pilot's `deploy` script names both:

```bash
npm run build    # react-router build: writes dist/client and dist/server
npm run deploy   # shopify hydrogen deploy --assets-dir dist/client --worker-dir dist/server
```

- The paths come from `buildDirectory: "dist"` in `react-router.config.ts`. React Router's default is `build/`; if you keep it, change both flags to match.
- `--assets-dir` and `--worker-dir` need `@shopify/cli` 4.4.0 or later. With 3.x the command fails on the unknown flags.
- Oxygen's GitHub workflow (`.github/workflows/oxygen-deployment-*.yml`) keeps running `npx shopify hydrogen deploy` with your deployment token; Pilot leaves it unchanged. See [Deploy to Oxygen](/guides/deployment/oxygen).

### `vite.config.ts`

```typescript
// Before
import { hydrogen } from "@shopify/hydrogen/vite";

plugins: [hydrogen(), oxygen(), reactRouter(), tailwindcss()],

// After
import { localHttps } from "@shopify/hydrogen/vite";
import { oxygen } from "@shopify/mini-oxygen/vite";

plugins: [
  // `npm run dev:https` serves https://local.tryhydrogen.dev
  localHttps({ enabled: process.env.npm_lifecycle_event === "dev:https" }),
  ...oxygen(), // returns an array: spread it
  reactRouter(),
  tailwindcss(),
],
ssr: {
  optimizeDeps: {
    // React and React Router must be pre-bundled for the workerd SSR runtime

      "react",
      "react/jsx-runtime",
      "react/jsx-dev-runtime",
      "react-dom",
      "react-dom/server",
      "react-router",
      "react-router > cookie",
      "react-router > set-cookie-parser",
    ],
  },
},
```

## Step 2: Run the Weaverse Codemod

`@weaverse/cli` 5.9.0 ships a codemod for `@weaverse/hydrogen` 6. Preview first:

```bash
npx @weaverse/cli@latest migrate v6 --dry-run
```

`--dry-run` lists the files it would change without writing them. Then apply it and review the diff:

```bash
npx @weaverse/cli@latest migrate v6
git diff
```

Use `--dir` to run it on another project folder. The codemod only touches files that import `@weaverse/hydrogen` or `@weaverse/next`, and does two things:

- **Moves imports** to the new entry points: `@weaverse/hydrogen` → `@weaverse/hydrogen/react-router`, `@weaverse/next` → `@weaverse/hydrogen/next`, `@weaverse/next/server` → `@weaverse/hydrogen/next/server`.
- **Renames types** listed in the table below.

<Warning>
  The renames are plain find-and-replace on whole words across each file that imports Weaverse. A local type with the same name, such as your own `ThemeSettingsResponse`, is renamed too. Review the diff before you commit.
</Warning>

### `@weaverse/hydrogen` 6 API Changes

**Entry points.** Hydrogen and React Router themes import everything from `@weaverse/hydrogen/react-router`, which re-exports the other public entries:

| Entry | Contents |
| --- | --- |
| `@weaverse/hydrogen/react-router` | Everything a Hydrogen theme uses: `WeaverseClient`, `withWeaverse`, `WeaverseHydrogenRoot`, `useThemeSettings`, `useTranslation`, `TranslationProvider`, `getSelectedProductOptions`, `getWeaverseSeoMeta`, `createSchema`, the hooks and the types |
| `@weaverse/hydrogen` | Schemas, data helpers and types, without React or a router |
| `@weaverse/hydrogen/react` | Framework-free React hooks: `useWeaverse`, `useItemInstance`, `useParentInstance`, `useChildInstances` |
| `@weaverse/hydrogen/next`, `@weaverse/hydrogen/next/server` | The Next.js SDK, also published as `@weaverse/next` 1.1.0 |

**Renamed types** (applied by the codemod):

| v5 | v6 |
| --- | --- |
| `HydrogenComponent` | `WeaverseComponent` |
| `HydrogenComponentProps` | `WeaverseComponentProps` |
| `HydrogenComponentSchema` | `WeaverseComponentSchema` |
| `HydrogenComponentData` | `WeaverseComponentData` |
| `HydrogenChildComponentReference` | `WeaverseChildComponentReference` |
| `HydrogenThemeSchema` | `WeaverseThemeSchema` |
| `HydrogenThemeSettings` | `WeaverseThemeSettings` |
| `HydrogenPageData` | `WeaversePageData` |
| `HydrogenPageAssignment` | `WeaversePageAssignment` |
| `HydrogenProjectType` | `WeaverseProjectType` |
| `ThemeSettingsResponse` | `WeaverseThemeSettingsResponse` |
| `ComponentLoaderArgs` | `WeaverseComponentLoaderArgs` |

**Removed from the public entries** (fix these by hand):

- `useThemeText`, `ThemeTextProvider` and `ThemeTextStore`, the deprecated aliases: use `useTranslation`, `TranslationProvider` and `TranslationStore`.
- `interpolate`, `createWeaverseDataContext`, `useWeaverseDataContext` and `WeaverseArticle` (`WeaverseArticle` had the same resource-picker shape as `WeaverseBlog`).
- `CachingStrategy`: import it from `@shopify/hydrogen`.
- `WeaverseHydrogen`, the runtime class. `useWeaverse()` still returns the runtime: type it with what you read, for example `useWeaverse<{ data: WeaversePageData }>()` (see [useWeaverse](/api-reference/use-weaverse)). `@weaverse/hydrogen/react-router` exports `WeaverseHydrogenRoot` and `withWeaverse`, which don't change.
- `WeaverseClient.withCache`, the classic Hydrogen `createWithCache()` instance. Call `weaverse.fetchWithCache()` instead: it fetches through Hydrogen's subrequest cache and returns the parsed JSON body.

  ```typescript
  // Before (v5)
  const { data } = await weaverse.withCache.fetch<Reviews>(url, init, {
    cacheKey: [url],
    cacheStrategy: CacheLong(),
    shouldCacheResponse: (body) => body != null,
  });

  // After (v6)
  import { Cache } from "@shopify/hydrogen";

  const data = await weaverse.fetchWithCache<Reviews>(url, {
    ...init,
    strategy: Cache.long(), // optional: 60 seconds fresh, a day stale by default
  });
  ```

  For a third-party URL, `fetchWithCache` resolves to `null` on an error status and rejects on a network failure. Check for `null` and keep a `.catch()` where the section should render without the data, as Pilot's `ali-reviews` section does.

**Behavior changes:**

- `WeaverseClient` takes the request's Storefront client plus `env`, `cache` and `waitUntil` instead of a spread classic Hydrogen context, and from 6.1.0 an optional `locale` for the market ([Step 5](#step-5-create-the-weaverseclient-from-the-storefront-client)).
- Section loaders query Shopify with `weaverse.storefront.graphql()`; there is no `query()` shim.
- `Env` extends the SDK's `WeaverseEnv` instead of Hydrogen's removed `HydrogenEnv`.
- `getSelectedProductOptions(request)` keeps its signature and still drops Weaverse's Studio query params.
- `@shopify/hydrogen` `>=2026.10.0` is now a peer dependency.
- Weaverse content keeps its caching: 60 seconds fresh, then up to a day stale while it revalidates or when the API fails.

## Step 3: Own the Request Lifecycle in the Server Entry

Classic `server.ts` built a Hydrogen context and handed the request to Hydrogen's handler. In 2026.10 it composes the lifecycle itself.

**Before (classic):**

```typescript
// server.ts
import * as remixBuild from "virtual:react-router/server-build";
import { storefrontRedirect } from "@shopify/hydrogen";
import { createRequestHandler } from "@shopify/hydrogen/oxygen";
import { createHydrogenRouterContext } from "~/.server/context";

export default {
  async fetch(request: Request, env: Env, executionContext: ExecutionContext) {
    const hydrogenContext = await createHydrogenRouterContext(request, env, executionContext);
    const handleRequest = createRequestHandler({
      build: remixBuild,
      mode: process.env.NODE_ENV,
      getLoadContext: () => hydrogenContext,
    });

    const response = await handleRequest(request);
    if (hydrogenContext.session.isPending) {
      response.headers.set("Set-Cookie", await hydrogenContext.session.commit());
    }
    if (response.status === 404) {
      return storefrontRedirect({ request, response, storefront: hydrogenContext.storefront });
    }
    return response;
  },
};
```

**After (Hydrogen 2026.10):**

```typescript
// server.ts
import { handleShopifyRedirects, handleShopifyRoutes } from "@shopify/hydrogen";
import { createRequestHandler, RouterContextProvider } from "react-router";
import * as serverBuild from "virtual:react-router/server-build";
import { cartHandlers, createPilotCartHandlers } from "~/.server/cart";
import { createAppContext } from "~/.server/context";
import { getCustomerAccountHandlers } from "~/.server/customer-account";
import { predictiveSearchHandlers } from "~/.server/predictive-search";
import { routeTemplates } from "~/utils/route-templates";

const handleRequest = createRequestHandler(serverBuild, process.env.NODE_ENV);

export default {
  async fetch(request: Request, env: Env, executionContext: ExecutionContext) {
    try {
      // 1. The request context and clients
      const appContext = await createAppContext(request, env, executionContext);
      const { session, storefront } = appContext;
      const requestContext = storefront.requestContext;

      // 2. Routes Hydrogen owns: /api/cart, predictive search, /account/login, ...
      const shopifyRoute = handleShopifyRoutes({
        request,
        requestContext,
        sessionManager: session,
        storefrontClient: storefront,
        routeTemplates,
        handlers: [
          createPilotCartHandlers({
            getCustomerAccessToken: appContext.customerAccount.getAccessToken,
          }),
          cartHandlers,
          predictiveSearchHandlers,
          getCustomerAccountHandlers(env),
        ],
      });
      if (shopifyRoute) {
        const response = await shopifyRoute;
        await commitSession(response, appContext);
        return response;
      }

      // 3. Render the app; loaders read `context.storefront`, `context.weaverse`, ...
      const routerContext = Object.assign(new RouterContextProvider(), appContext);
      const response = await handleRequest(request, routerContext);

      // 4. On a 404, look the path up in Shopify's URL redirects
      if (response.status === 404) {
        const redirect = await handleShopifyRedirects({
          request,
          storefrontClient: storefront,
          routeTemplates,
        });
        if (redirect) return redirect;
      }

      // 5. Commit the session, then apply Shopify's response headers
      await commitSession(response, appContext);
      requestContext.applyResponseHeaders(response.headers);
      return response;
    } catch (error) {
      console.error(error);
      return new Response("An unexpected error occurred", { status: 500 });
    }
  },
};

async function commitSession(
  response: Response,
  { session }: Awaited<ReturnType<typeof createAppContext>>,
) {
  const headers = new Headers((await session.commit()) ?? undefined);
  for (const [name, value] of headers) response.headers.append(name, value);
}
```

Notes:

- `handleShopifyRoutes` decides synchronously: it returns a `Promise<Response>` for a path a handler owns, otherwise `null`. Check it without `await`.
- Handlers are matched in order, so app handlers that wrap a library handler (Pilot's `POST /api/cart` syncs the cart's market, then calls `cartHandlers.post`) go first.
- `routeTemplates` comes from `createShopifyRouteTemplates()` and maps Shopify resources to your routes, for `?variant=` links, URL redirects and `ShopifyScripts`. Omitting it, or `applyResponseHeaders`, fails silently.
- Pilot's real `server.ts` also skips the redirect lookup for unsupported markets, makes the lookup market-aware ([Markets](#markets)), and leaves cart permalinks without a `payment` param to its own `/cart/:lines` route.

## Step 4: Build the App Context Yourself

`createHydrogenContext()` is gone. Pilot replaces `createHydrogenRouterContext()` with `createAppContext()` in `app/.server/context.ts`, which builds the same values and returns a plain object that `server.ts` copies onto React Router's context:

```typescript
// app/.server/context.ts
export async function createAppContext(
  request: Request,
  env: Env,
  executionContext: ExecutionContext,
) {
  const waitUntil = executionContext.waitUntil.bind(executionContext);
  const [cache, session] = await Promise.all([
    caches.open("hydrogen"),
    AppSession.init(request, [env.SESSION_SECRET]),
  ]);
  const storefront = createRequestStorefront({ request, env, cache, waitUntil });
  const customerAccount = createCustomerAccount({ env, request, session, storefront });
  const weaverse = new WeaverseClient({ /* Step 5 */ });

  return { env, cache, waitUntil, session, storefront, customerAccount, weaverse };
}

export type AppContext = Awaited<ReturnType<typeof createAppContext>>;
```

### The Storefront Client

`createRequestStorefront()` (Pilot's `app/.server/storefront.ts`) builds a request-scoped client. It uses the private token when Oxygen injects one, and the public token otherwise:

```typescript
import {
  type CachingStrategy,
  createShopifyRequestContext,
  createStorefrontClient,
  type PublicStorefrontClient,
  type RequestScopedPrivateStorefrontClient,
} from "@shopify/hydrogen";

// The bare client types drop `cache` from `graphql()` options; carry it.
type StorefrontCallOptions = { cache?: CachingStrategy };

export function createRequestStorefront({ request, env, cache, waitUntil }) {
  const i18n = getRequestI18n(request); // { country, language, pathPrefix, ... }
  const buyerIp = getBuyerIp(request.headers); // `oxygen-buyer-ip`, then proxy headers
  const config = {
    storeDomain: env.PUBLIC_STORE_DOMAIN,
    storefrontId: env.PUBLIC_STOREFRONT_ID || undefined,
    cache,
    waitUntil,
  };

  if (env.PRIVATE_STOREFRONT_API_TOKEN && buyerIp) {
    return createStorefrontClient({
      type: "private",
      requestContext: createShopifyRequestContext({ request, i18n, buyerIp }),
      config: { ...config, privateStorefrontToken: env.PRIVATE_STOREFRONT_API_TOKEN },
    });
  }

  return createStorefrontClient({
    type: "public",
    requestContext: createShopifyRequestContext({ request, i18n }),
    config: { ...config, publicStorefrontToken: env.PUBLIC_STOREFRONT_API_TOKEN },
  });
}
```

`getRequestI18n` and `getBuyerIp` are app code. Pilot resolves the market from the URL prefix, or from the `Referer` for unprefixed handler paths ([Markets](#markets)).

### The Session

The session is now any object that implements Hydrogen's `WritableCustomerSessionManager` (`getSessionOrigin`, `getSessionItem`, `setSessionItem`, `removeSessionItem`, plus an optional `commit()` returning cookie headers). Pilot's `AppSession` in `app/.server/session.ts` wraps React Router's `createCookieSessionStorage` and only commits when something changed, so anonymous pages never get a `Set-Cookie` that would make them uncacheable. An in-memory session works for carts but cannot complete Customer Account login, which spans two requests.

```typescript
/// <reference types="vite/client" />
/// <reference types="react-router" />
/// <reference types="@shopify/oxygen-workers-types" />
import type { WeaverseEnv } from "@weaverse/hydrogen/react-router";
import type { AppContext } from "./app/.server/context";
```

### The `locale` Option

Weaverse needs the request's market for three things: the locale it sends with page requests, the Translation Manager overrides it loads (keyed by `${language}-${country}`, lowercased) and the `requestInfo.i18n` Studio reads. By default it takes them from `storefront.i18n`. From `@weaverse/hydrogen` 6.1.0, `locale` overrides that without touching the Storefront client:

- **Pass it** when the Storefront client's `i18n.language` is a Shopify `LanguageCode` that differs from the market's public language. Shopify wants `ZH_TW` for a Traditional Chinese Hong Kong market; handed to Weaverse, that asks for `zh_tw-hk` translations, which match nothing and silently fall back to the theme defaults.
- **Include `pathPrefix`**, which Weaverse passes to Studio. The value is a `WeaverseI18n`: Hydrogen's `I18nConfig` (`language`, `country`) plus optional `pathPrefix`, `label` and any other market fields.
- **Leave it out** when `storefront.i18n` already carries the public language and `pathPrefix`. Nothing changes from 6.0.

Pilot passes its canonical market for the request, `resolveRequestLocale(request)` from `app/.server/storefront.ts`, which reads the URL prefix (or the `Referer` for unprefixed handler paths) and returns an entry of `SUPPORTED_LOCALES`. The same function, with the language swapped for the Shopify code, builds the Storefront client's `i18n`. `weaverse.storefront` stays the same client as `context.storefront`, so section loaders still query Shopify in its `LanguageCode`.

<Note>
  On 6.0, Pilot handed `WeaverseClient` a copy of the Storefront client with a relabelled `i18n` (`weaverseStorefront()`). Pilot replaced it with `locale` when it moved to 6.1.0 ([Weaverse/pilot#214](https://github.com/Weaverse/pilot/pull/214)). If your theme copied that helper, delete it and pass `locale`.
</Note>

## Step 6: Move Queries to the New GraphQL Client

GraphQL codegen is replaced by `gql()`: TypeScript infers result and variable types from Hydrogen's bundled Storefront API schema, and `hydrogen gql check` validates every document.

**Before (classic):**

```typescript
import type { ProductQuery } from "storefront-api.generated";

const PRODUCT_QUERY = `#graphql
  query product($country: CountryCode, $language: LanguageCode, $handle: String!)
  @inContext(country: $country, language: $language) {
    product(handle: $handle) { ...ProductDetails }
  }
  ${PRODUCT_FRAGMENT}
` as const;

const { product } = await storefront.query<ProductQuery>(PRODUCT_QUERY, {
  variables: {
    handle,
    country: storefront.i18n.country,
    language: storefront.i18n.language,
  },
  cache: storefront.CacheLong(),
});
```

**After (Hydrogen 2026.10):**

```typescript
import { gql, type StorefrontApi } from "@shopify/hydrogen";
import { CACHE_LONG } from "~/utils/cache";
import { unwrapStorefront } from "~/utils/storefront";

const PRODUCT_QUERY = gql(
  `
  query product($country: CountryCode, $language: LanguageCode, $handle: String!)
  @inContext(country: $country, language: $language) {
    product(handle: $handle) { ...ProductDetails }
  }
`,
  [PRODUCT_FRAGMENT], // fragments are passed, not interpolated
);

export type ProductQuery = StorefrontApi.ResultOf<typeof PRODUCT_QUERY>;

const { product } = await storefront
  .graphql(PRODUCT_QUERY, { variables: { handle }, cache: CACHE_LONG })
  .then(unwrapStorefront);
```

What changes at every call site:

- **`$country` and `$language` are injected** from the request context. Drop them from `variables`.
- **`graphql()` returns `{ data, errors, headers }`** and does not throw on GraphQL errors. Pilot keeps the throwing behavior with a small helper:

  ```typescript
  // app/utils/storefront.ts
  import type { GraphQLFormattedError } from "@shopify/hydrogen";

  export function unwrapStorefront<T>(result: {
    data: T | null;
    errors?: GraphQLFormattedError[];
  }): T {
    if (result.errors?.length || !result.data) {
      const messages = result.errors?.map(({ message }) => message) ?? ["No data returned"];
      throw new Error(`[storefront.graphql] ${messages.join("\n")}`);
    }
    return result.data;
  }
  ```

- **There is no default cache.** Pass `cache` on every query, or it hits the API on every request. Pilot maps the classic strategies in `app/utils/cache.ts`:

  ```typescript
  import { Cache } from "@shopify/hydrogen";

  // Classic Hydrogen's implicit default: fresh for a second, stale for a day
  export const CACHE_DEFAULT = Cache({ mode: "public", maxAge: 1, staleWhileRevalidate: 86_399 });
  export const CACHE_SHORT = Cache.short();
  export const CACHE_LONG = Cache.long();
  export const CACHE_NONE = Cache.none();
  ```

  `generateCacheControlHeader` is gone too; Pilot builds `Cache-Control` values from these strategies with a local `cacheControlHeader()`.

### Section Loaders

Section loaders keep `{ data, weaverse }`; `weaverse.storefront` is the 2026.10 client.

**Before (v5):**

```typescript
import { type ComponentLoaderArgs } from "@weaverse/hydrogen";
import type { CollectionsByIdsQuery } from "storefront-api.generated";

export const loader = async ({ data, weaverse }: ComponentLoaderArgs<FeaturedCollectionsData>) => {
  const { nodes } = await weaverse.storefront.query<CollectionsByIdsQuery>(COLLECTIONS_QUERY, {
    variables: { ids },
  });
  return nodes.filter(Boolean);
};
```

**After (v6):**

```typescript
import { gql } from "@shopify/hydrogen";
import { type WeaverseComponentLoaderArgs } from "@weaverse/hydrogen/react-router";
import { CACHE_DEFAULT } from "~/utils/cache";
import { unwrapStorefront } from "~/utils/storefront";

const COLLECTIONS_QUERY = gql(`
  query collectionsByIds($country: CountryCode, $language: LanguageCode, $ids: [ID!]!)
  @inContext(country: $country, language: $language) {
    nodes(ids: $ids) { ... on Collection { id title handle } }
  }
`);

export const loader = async ({ data, weaverse }: WeaverseComponentLoaderArgs<FeaturedCollectionsData>) => {
  const { nodes } = unwrapStorefront(
    await weaverse.storefront.graphql(COLLECTIONS_QUERY, {
      variables: { ids },
      cache: CACHE_DEFAULT,
    }),
  );
  return nodes.filter((node) => Boolean(node && "id" in node));
};
```

`gql()` results are typed precisely, including nullable and union fields such as `nodes(ids:)`. Narrow them where you read them instead of casting to `any`.

Customer Account documents use `gql` from `@shopify/hydrogen/customer-account`, with `InferResult<SourceOf<typeof DOC>>` for their result types.

**Before (classic):**

Read state with selectors, for example `useCart((state) => state.data)`, `useCart((state) => state.pending.lines.has(line.id))` and `useCart((state) => state.errors)`. After an app-owned change (a gift card, a market switch), call `refresh()` from `useCartActions()`.

```tsx
import { type ValidProductSelectionResult } from "@shopify/hydrogen";

export default function Product() {
  const { product } = useLoaderData<typeof loader>();
  const navigate = useNavigate();
  const { pathname, search } = useLocation();

  // A selection updates every section at once; the URL follows with a
  // client-side replace. A variant the page already loaded needs no loader run.
  function handleSelect(result: ValidProductSelectionResult<ProductFormData>) {
    const path = productOptionPath(
      product,
      result.selectedOptions,
      result.selectedVariant?.product?.handle, // combined listings link to the other product
      new URLSearchParams(search),

    navigate(localizePath(path, resolveLocale(pathname)), {
      replace: true,
      preventScrollReset: true,
      ...(result.status === "resolved" ? { defaultShouldRevalidate: false } : {}),

      <WeaverseContent />
```

## Markets

Pilot keeps one list of markets, `SUPPORTED_LOCALES` in `app/utils/locale.ts`, and serves them as URL prefixes (`/fr-fr/products/...`). Three parts change on 2026.10.

### Locale-Prefixed Routes

Routes still sit under `prefix(":locale?", [...])`. The request's market becomes the `i18n` of `createShopifyRequestContext()`, and `storefront.graphql()` fills `$country` and `$language` from it.

Hydrogen's handler paths (`/api/cart`, `/api/predictive-search`, `/account/login`, ...) are exact and never carry a prefix. Pilot resolves their market from the same-origin `Referer` instead (and from `return_to` for `/account/login`), falling back to the default market.

Shopify's URL redirects are stored on market-neutral paths, and `handleShopifyRedirects` only matches document paths. Pilot's `marketAwareRedirect()` (`app/.server/market-redirect.ts`) looks redirects up on the neutral path, re-prefixes the target, and answers single-fetch `.data` requests with `204` and `X-Remix-Redirect`, as classic `storefrontRedirect` did.

<Note>
  Chinese markets need two language codes: Shopify wants its `LanguageCode` (`ZH_TW`), while Weaverse keys translations by the public locale (`zh-tw`). Pilot gives the Storefront client the Shopify code and passes the public market to `WeaverseClient` as `locale` ([Step 5](#the-locale-option)). `graphql()` reads `$language` from the request context, so Shopify still receives `ZH_TW`.
</Note>

### Unsupported Markets Answer 404

A market-shaped prefix the store doesn't sell in (`/en-xx/products/hoodie`) must not render the default market's catalogue at an unlimited number of URLs. Pilot uses **two layout routes**, because page routes and resource routes run differently:

```typescript
// app/routes/market-guard.ts — wraps the `:locale?` page routes
export function loader({ request }: LoaderFunctionArgs) {
  if (isUnsupportedMarketPath(new URL(request.url).pathname)) {
    throw new Response("page", { status: 404 });
  }
  return null;
}
```

```typescript
// app/routes/market-guard-resources.ts — wraps the `:locale?` resource routes
function guardMarket({ request }: { request: Request }, next: () => Promise<Response>) {
  if (isUnsupportedMarketPath(new URL(request.url).pathname)) {
    throw new Response(null, { status: 404 });
  }
  return next();
}

export const middleware: MiddlewareFunction<Response>[] = [guardMarket];
```

- **Pages** throw from a layout loader below the root route. The root loader's data survives, so the root `ErrorBoundary` renders the regular 404 page inside the header and footer, for documents and `.data` navigations alike. A 404 from `server.ts` would have no header or footer.
- **Resource routes** (APIs, sitemaps, `/discount/:code`, `/cart/checkout`) need the second layout. A resource-route request runs only that route's loader, never the page guard's, so the check runs as middleware, which React Router calls for every matched route. It needs `future.v8_middleware: true`.

`server.ts` also skips the redirect lookup for unsupported market paths, which would otherwise fall back to the default market.

### Switching the Cart's Market

A cart keeps the country it was created in. If the shopper switches market, the cart keeps the old market's prices and taxes until its buyer identity changes. Pilot handles this in two places:

- Its `POST /api/cart` handler calls `cartBuyerIdentityUpdate` with the request's country (and the customer's access token) before every cart change.
- The country selector posts the new country to `/api/cart/buyer-identity` while it navigates, then refreshes the store and `window.Shopify`:

  ```typescript
  // app/components/layout/country-selector/market-form.tsx
  async function handleSubmit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    syncShopifyMarket(locale); // before navigating, so the next page view reports the new market
    await Promise.all([
      navigate(redirectTo),
      fetch(CART_BUYER_IDENTITY_PATH, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ countryCode: locale.country }),
      }).catch(() => null),
    ]);
    refresh(); // from useCartActions()
  }
  ```

  Without JavaScript, the same form posts to `/api/cart/buyer-identity`, which updates the cart and redirects.

## Common Pitfalls

<AccordionGroup>
  <Accordion title="The codemod renamed one of my own types">
    The renames match whole words in every file that imports Weaverse. A local `ThemeSettingsResponse` becomes `WeaverseThemeSettingsResponse` too. Run with `--dry-run` first and review `git diff` after applying.
  </Accordion>
  <Accordion title="Weaverse components lose their data after the upgrade">
    Two copies of `@weaverse/react` are installed. Keep `@weaverse/react` and `@weaverse/next` on the versions your `@weaverse/hydrogen` pins (6.1.0 pins `@weaverse/react` 6.1.0 and `@weaverse/next` 1.1.1), and check with `npm ls @weaverse/react`.
  </Accordion>
  <Accordion title="Translations show the theme defaults in one market">
    Weaverse asked for the wrong locale key. If the Storefront client's `i18n.language` is a Shopify code such as `ZH_TW`, pass the market's public locale to `WeaverseClient` as `locale` (`@weaverse/hydrogen` 6.1.0 or later). See [The `locale` option](#the-locale-option).
  </Accordion>
  <Accordion title="weaverse.withCache is undefined">
    `WeaverseClient` no longer carries a classic `createWithCache()` instance. Call `weaverse.fetchWithCache(url, { ...init, strategy })`, which returns the parsed body ([Step 2](#step-2-run-the-weaverse-codemod)).
  </Accordion>
  <Accordion title="shopify hydrogen deploy fails on --assets-dir or finds no build">
    The flags need `@shopify/cli` 4.4.0 or later, and the directories must match `buildDirectory` in `react-router.config.ts`. Run `npm run build` first; with `buildDirectory: "dist"` it writes `dist/client` and `dist/server`.
  </Accordion>
  <Accordion title="Pages hit the Storefront API on every request">
    Hydrogen 2026.10 has no default cache. Pass `cache` to every `storefront.graphql()` call.
  </Accordion>
  <Accordion title="A failed query renders a half-empty page">
    `graphql()` returns `errors` instead of throwing. Check `errors` or unwrap the result as in [Step 6](#step-6-move-queries-to-the-new-graphql-client).
  </Accordion>
  <Accordion title="Shopify headers or redirect targets are missing">
    `requestContext.applyResponseHeaders()` must run on the normal response path, and `routeTemplates` must reach both `handleShopifyRoutes` and `handleShopifyRedirects`. Both fail silently.
  </Accordion>
  <Accordion title="Error: requestContext.buyerIp is required for private Storefront API clients">
    The private client needs the buyer IP on the request context. Read it from `oxygen-buyer-ip` (or your proxy's header), or fall back to the public client as Pilot does.
  </Accordion>
  <Accordion title="Login links land on the account catch-all route">
    `/account/login` and the other handler paths must be reached with a full document request. Use `<a>`/`<form>`, and `redirectDocument` when redirecting from a loader.
  </Accordion>
  <Accordion title="The cart shows old totals after a /discount/:code link">
    The cart store loads the cart once, on mount. The `/discount/:code` loader must end with `redirectDocument` (not `redirect`), so a client-side link to it reloads the page and the store.
  </Accordion>
  <Accordion title="Products are priced in the store's primary currency in one market">
    With `@inContext(country:)`, Shopify silently falls back to the store's primary country when the store doesn't sell to that country, while a cart whose `buyerIdentity.countryCode` is that country prices in its currency. This is store configuration, not a code bug: add the country to a Market in Shopify admin.
  </Accordion>
  <Accordion title="Customer access tokens on carts break vite dev">
    In `@shopify/hydrogen` 2026.10.2, the `./customer-account` export has no `development` condition, and passing `customerSession` to `createCartServerHandlers` breaks under `vite dev`. Pilot attaches `customerAccessToken` in its own `POST /api/cart` handler instead.
  </Accordion>
  <Accordion title="Loading components through Vite ssrLoadModule fails on extensionless imports">
    If a script loads your component registry or manifest through Vite's `ssrLoadModule`, packages that publish ESM with extensionless relative imports (such as `react-use/esm/*`) fail under Node's ESM resolver. Add them to `ssr.noExternal` in that Vite server config, as Pilot's `other/weaverse-manifest.mjs` does with `noExternal: [/^@weaverse\//, "react-use"]`.
  </Accordion>
  <Accordion title="Hydration is silently dead (cart, variant picker, analytics)">
    The nonce was dropped while porting CSP. Pass the nonce to `ShopifyScripts`, `Scripts` and `ScrollRestoration`, and check the console for CSP violations. See [Content Security Policy](/features/content-security).
  </Accordion>
  <Accordion title="Anonymous pages are no longer cached">
    Something personalized reached the document: a cart passed as `CartProvider` `initialData`, a customer token in a loader, or a session committed on every response. Load the cart after hydration and commit the session only when it changed.
  </Accordion>
</AccordionGroup>

## Migration Checklist

- `@shopify/hydrogen` `^2026.10`, `@weaverse/hydrogen` `^6.1`, React Router 7.18+ on one version, Vite 8
- Scripts: `vite dev`, `dev:https`, `react-router build`, `vite preview`, `shopify hydrogen deploy --assets-dir dist/client --worker-dir dist/server`; `@shopify/cli` 4.4.0 or later
- `vite.config.ts` without `hydrogen()`; `react-router.config.ts` with `buildDirectory: "dist"` and `v8_middleware`
- GraphQL codegen removed; `@shopify/hydrogen/ts-plugin` and `hydrogen gql check` in place
- `npx @weaverse/cli@latest migrate v6` applied and its diff reviewed
- `server.ts` composes the request lifecycle: `handleShopifyRoutes`, session commit, `applyResponseHeaders`, `handleShopifyRedirects`
- `WeaverseClient` built from the request's Storefront client, with `locale` when the market's public language differs from the Shopify `LanguageCode` (6.1.0+)
- No `WeaverseHydrogen` import and no `weaverse.withCache`; third-party fetches use `weaverse.fetchWithCache()`
- Every query is a `gql()` document run with `storefront.graphql()`, checks `errors`, and passes `cache`
- `hydrogenRoutes()` removed, classic cart and auth routes deleted, market guard layouts added
- Cart on `createCartServerHandlers` and `createCartComponents`; no `CartForm`
- Product pages on `ProductProvider` and `useProductForm`; no `useOptimisticVariant`
- `ShopifyScripts`, route trackers and `useCartAnalytics` in place of `Analytics.*`
- Customer Account handlers registered; login over `dev:https` works
- `Image`, `Money`, `getSeoMeta`, sitemaps, `Pagination` and CSP ported
- `npm run typecheck` and `npm run build` pass; Studio preview, design mode and section loaders work
